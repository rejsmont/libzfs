# scenarios/

Shell-based **real-world** test scenarios for `libzfseasy` + `zfsbackup`. The pool scripts drive real ZFS pools
on this host (with `sudo`); the `test_*.sh` harnesses run in disposable Multipass VMs named
`zfsb-*` that they create, reuse and, with `--purge`, delete (`test_install_deb.sh` always starts from fresh `zfsb-pkg*` VMs) — they never touch ZFS on the host. They are slow,
side-effectful, and require ZFS or Multipass (and `git`; `test_install.sh` also `poetry`; `test_install_deb.sh` also needs the Linux build VM `zfsb-deb`). Run them from the
**repository root**; `-h`/`--help` prints a VM harness's header (its full description and usage).

The mocked/`real_zfs` **pytest** suites live under [`tests/`](../tests/), not here.

## Scripts

| Script | What it does |
|---|---|
| [`setup_test_pool.sh`](setup_test_pool.sh) | Create a file-backed test pool (sparse image; `sudo zpool create`) and delegate `zfs`/`zpool` permissions to the current user, one permission at a time (a permission the installed ZFS does not know, e.g. `inherit` on OpenZFS 2.4, is skipped with a warning instead of aborting). Asks before destroying an existing pool or overwriting an existing image. For manual experiments: the pytest `real_zfs` tier creates its own pool and does not use this one. Env: `TEST_ZFS_POOL` (default `testpool`), `ZFS_TEST_DISK` (default `/tmp/zfs-test-disk`), `ZFS_TEST_SIZE` (MB, default 512). |
| [`cleanup_test_pool.sh`](cleanup_test_pool.sh) | Destroy the pool created by `setup_test_pool.sh` and remove its backing image, after a `yes` prompt (it also offers to remove an image left without a pool). Same `TEST_ZFS_POOL` / `ZFS_TEST_DISK`. |
| [`create_test_pool.sh`](create_test_pool.sh) | `create_test_pool.sh [pool]` (default `libzfs_test`): a 512 MB pool on `/tmp/zpool_<pool>.img` with nested datasets (`mountpoint=none`) matching [`../zfsbackup/config.example.yaml`](../zfsbackup/config.example.yaml), with permissions delegated to the current user. Refuses an existing pool; prints the command that destroys it. |

## Shipped-tree layout (the packaging split)

`libzfseasy` lives in `libs/libzfseasy/libzfseasy/` (its own `pyproject.toml`); the root `pyproject.toml` builds only
`zfsbackup`. Every harness that runs a shipped tree from source (`test_two_vm_backup.sh` including its L1 old and
hostile trees, `test_config_permissions.sh` and its systemd unit, `test_hung_pool.sh`, the pytest tier in
`test_openzfs_matrix.sh`) therefore sets `PYTHONPATH=<tree>:<tree>/libs/libzfseasy`. A path that does not exist is
harmless, so the same setting runs a tree from an earlier ref with `libzfseasy/` at the root. `test_install.sh` builds
the wheels instead: `poetry build` at the root and in `libs/libzfseasy`, installed together (see its row above).

## macOS / Multipass caveats

These bit us repeatedly; the two-VM harness already works around them, but keep them in mind when
editing these scripts:

- **Never redirect a `multipass exec`'s *host* stdout to `/dev/null`** — the exec wedges and becomes
  unkillable. Discard output *inside the guest* instead (e.g. `... -o /dev/null`, or
  `sh -c '... >/dev/null 2>&1'`).
- **Deliver config via `multipass transfer`, not heredoc-piped stdin** (`multipass exec ... tee`) —
  piping on host stdin hangs/spins.
- **A guest command that exits with status 4 hangs `multipass exec` forever** (verified: `exit 4`
  wedges, 2/3/104 do not). It bites `systemctl is-active` on a unit that no longer exists (exit 4 on
  current systemd) and pytest's usage error (exit 4). `test_config_permissions.sh`, `test_install.sh`,
  `test_hung_pool.sh` and `test_openzfs_matrix.sh` run guest commands in an inner shell that remaps
  4 to 104; do the same in any new Multipass code that probes unit state or runs pytest.
- `multipass purge` is global (it destroys every deleted VM, not just yours); prefer
  `multipass delete --purge <vm>` for a single VM.
